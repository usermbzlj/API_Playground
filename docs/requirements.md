LLM API Playground：开发目标与需求说明
文档用途：交给负责调研、设计和开发的 AI Agent，作为项目目标、产品边界和验收方向。
性质：目标导向的需求说明，不是技术设计书、固定排期或接口规格。
版本：初始需求（2026-10-21）。后续应随实际探索持续更新。

0. 给开发 Agent 的任务说明
请围绕本文目标，自行开展必要的资料检索、技术论证、原型验证、架构设计、开发和测试，最终交付一个可实际使用、易于扩展的 LLM / AI API 游乐场。

你可以主动提出更好的产品形态、交互方法和实现策略，也可以调整功能组织方式与开发先后顺序。不要把下文提到的框架、页面、接口、厂商名单或实验玩法视作必须照搬的工程方案。

但是，不要以“统一聊天客户端”替代本项目的核心诉求；不要为了快速支持大量模型而抹掉厂商的原生特色。需要区分：用户明确提出的需求、调研得到的事实、尚待验证的假设，以及可自由发挥的创意。
1. 项目愿景
我要一个玩各种 AI API 的游乐场：可以非常方便地接入国内外大模型厂商及其不同模型，尤其能够深入体验、研究和比较各家 API 独有或相对少见的能力、参数、交互模式和多模态功能。

这不是只换模型的聊天框，也不是只看排行榜的评测网站。它应该像一个综合 AI 实验室：想试一个新模型、某个奇特参数、一次实时语音对话、一个视频生成工作流、某种代码补全机制或一个工具调用协议，都能快速找到入口，直观看到效果，必要时还能深入观察底层调用细节。

核心价值排序（表达方向而非僵硬的分数权重）：
1. 好玩、方便、可探索：低门槛快速试到真功能，能激发继续实验的兴趣。
2. 原生特色不丢失：针对不同厂商与模型做有深度的专属适配，而不是强行取它们能力的交集。
3. 不限文本：图像、音频、视频、实时交互、视觉理解、3D、Embedding/Rerank、工具调用等，只要存在值得玩的 API，就有探索空间。
4. 真实、透明、可复现：知道到底调用了什么、哪些参数生效、结果和花费如何；实验可以保存、重试和对比。
5. 持续扩展：新厂商、新模型、新协议、新模态、新特性出现后，不需要推翻整个项目。
2. 典型使用体验
以下是期望能够完成的事情，不要求用固定的菜单结构实现：
- 我听说某家发布了新模型：打开游乐场，找到厂商/模型，看见它支持的功能、访问前提、定价或成本提示，并很快完成第一次实际调用。
- 我发现一个有意思的 API 特性：按“特性”而不只按“厂商”浏览，例如 FIM 补全、对话前缀续写、Next Edit、推理强度、Logprobs、视频首尾帧、语音情绪、实时双向音频等，直接进入贴合该能力的实验界面。
- 我想深入研究行为差异：修改原生参数、输入或参考素材，运行多次，观察输出、流式事件、延迟、Token 使用、费用、失败原因和厂商响应字段。
- 我想比较实现方式：让不同厂商、模型、协议或不同参数版本在尽可能公平的条件下进行对照；同时清楚标注哪些地方本来就不可直接等价。
- 我想试小众厂商：即使还没有专门适配，也可以通过自定义连接方式、请求模板或通用协议进行初步尝试，之后再逐步升级成原生适配。
- 我关掉页面后再回来：仍能找到之前的实验记录、输入素材、生成产物和未完成的异步任务（在技术和服务商条件允许时）。
3. 厂商覆盖：广、深并重
3.1 关注范围
国内重点（示例，不封闭名单）：MiniMax、小米 MiMo、Kimi / Moonshot、豆包 / 火山方舟、DeepSeek、阿里 Qwen / 百炼、智谱 GLM / BigModel、阶跃星辰 StepFun、腾讯混元、百度文心 / 千帆、科大讯飞星火、蚂蚁百灵 Ling / Ring、美团 LongCat、商汤 SenseNova、百川智能、360 智脑等。

国内多模态及垂直厂商（示例）：可灵 Kling、Vidu、PixVerse、Fish Audio、Tripo 等，以及后续值得发现的小型、专精或新兴服务商。

国际厂商（示例）：OpenAI、Anthropic、Google Gemini、xAI、Mistral、Inception Labs、Cohere、Voyage AI、ElevenLabs、Stability AI、Black Forest Labs、Runway、Luma 等。

聚合与推理平台（示例）：硅基流动、OpenRouter、Together、Fireworks、Groq、Cerebras、Replicate、fal.ai、Hugging Face Inference Providers，以及国内提供第三方模型调用的聚合服务。

不追求一开始机械地接完所有名单。希望优先研究新颖、差异明显、可实际调用、有实验价值的服务，并随着调研不断发现更多有趣的小厂商。
3.2 厂商、模型、API 服务不是一回事
需要理解并呈现以下差异：
- 模型开发方：谁开发了模型、它具有什么理论能力。
- 实际 API 提供方：官方、云平台还是聚合路由，实际开放哪些端点、参数和权限。
- 具体模型/快照/部署：同一品牌不同模型的上下文、模态、思考开关、工具、接口常常不一致。
- 账户与地域条件：有些能力需要白名单、余额、特定地域或不同套餐。
同一个模型通过不同服务商访问时，不能想当然认为特性、价格、速度、限制完全相同。应以实际可调用的提供商—端点—模型组合为准。
3.3 深度适配的含义
对重点厂商，期望不仅能发一条文本消息，还能够：
- 发现、理解并利用它自己的原生 API、可选参数、协议形式、内容结构和高级操作。
- 明确区分厂商级、模型级、端点级、账户级的能力与限制。
- 针对真正特殊的功能提供专属交互方式；普通参数不必为每个厂商重复造一套 UI。
- 保留厂商响应的特殊信息，不为了适配统一格式而静默丢弃。
- 不能做的功能就诚实说明，而不是用外观相似的普通文本调用假装支持。
4. 能力范围：全模态、全形态探索
这些是需要考虑的能力类别，不是穷举列表，Agent 应根据真实 API 继续扩充。
4.1 文本、代码与推理
普通对话与流式生成；多轮上下文；系统/开发者指令；结构化输出；工具/函数调用；原生搜索或代码执行；FIM 中间补全、Assistant 前缀续写、下一步编辑预测、预测输出；思考模式、推理预算、推理内容返回方式；Token 概率与候选；上下文缓存；批处理；长上下文；Embedding、Rerank、文档解析等。
4.2 图像与视觉理解
文生图、图生图、局部编辑、扩图、参考图、风格与一致性控制；图片理解、OCR、文档/图表理解；图像尺寸、质量、种子、蒙版、多图引用等厂商原生参数。
4.3 音频与实时交互
TTS、ASR、声音设计、经授权的音色复刻、情绪或语气控制、语音转语音、音频理解、实时双向语音、WebSocket 流式交互、打断、延迟、转写、音频片段与字幕对齐等。
4.4 视频与时序内容
文生视频、图生视频、视频理解、视频编辑与延长、首尾帧、参考视频、角色/主体一致性、多镜头分镜、音画同步、异步任务、进度查询、结果获取和任务失败诊断。
4.5 3D、动作与其他新模态
文本/图像到 3D、网格/贴图/绑骨/动画等；未来若出现空间、动作、机器人、交互式环境等值得体验的 API，也不要因最初的分类设计而无法接入。

重要： 以上不是要求每一个厂商都实现所有模态，而是让系统能容纳不同模态及其专用实验体验。
5. 特性体验的产品要求
5.1 两种发现路径
- 按厂商/模型探索：我想看看 Kimi、MiMo、MiniMax、豆包各自有什么好玩的。
- 按能力/玩法探索：我想试 FIM、视频分镜、情绪合成、实时语音或下一步编辑，不一定先知道哪家提供。
能力详情最好能告诉我：是什么、适合干什么、哪些模型与端点支持、限制和成本、示例输入、怎么开始。信息不足应标记待验证。
5.2 简单体验与深入实验可无缝切换
同一个能力既要能“一键试一下”，也要允许深入调整原生参数。复杂能力可以拥有专属工作台，例如：
- 代码中间补全：在编辑器里分别编辑前缀、空缺和后缀。
- 对话前缀续写：指定已经写出的 Assistant 开头并观察续写。
- Token 概率：查看候选 Token、概率和生成过程（仅在 API 确实开放时）。
- 推理控制：对比不同预算/开关/上下文保留方式；标明参数是否实际生效。
- 工具调用：查看工具选择、入参、执行结果与时序。
- 实时语音：播放与录音、打断测试、波形、延迟和事件观察。
- 视频生成：素材上传、分镜/时间轴、参考物、任务队列、结果预览。
- 3D 生成：旋转、缩放、材质/网格预览和生成产物管理。
这些只是交互灵感。应根据模型的真实接口，设计最自然、最轻便的操作，不要为了炫技强行复杂化。
5.3 原始 API 调试必须方便
希望有一层足够透明的API Inspector，能在安全脱敏后查看：实际端点和请求参数、Headers 的非敏感部分、原始 JSON / 流式事件 / WebSocket 消息、工具调用、异步任务状态、错误响应和返回的特殊字段。

用户应能够从友好表单深入到原生请求，必要时修改高级字段、复制脱敏请求示例、复现一次实验。不要为了统一显示而隐藏供应商行为差异。
5.4 对比与复现
支持保存参数组合、输入素材、提示词、模型版本、时间、输出、消耗信息与实验备注；便于复用、复制变体、并排对比。对比可以是同模型不同参数，也可以是不同供应商的同类能力。

衡量体验时可以观察首 Token/首音频时间、总耗时、输出速率、请求量、Token/缓存命中、估算或真实费用、失败率等；但要避免把厂商未提供的指标伪装成精确事实。
6. API 接入与系统演进原则
- 原生优先，通用兜底：OpenAI 兼容等统一协议有价值，但不能成为所有能力的天花板。
- 能力驱动而非名称驱动：模型名、商标和价格会更新；能力及约束应尽可能与 UI 解耦、可维护。
- 原始与标准化并存：统一基本操作以降低使用成本，同时保留原生参数、原始请求和特殊返回。
- 多种调用生命周期并存：一次性 HTTP、SSE、WebSocket、文件上传、异步创建/查询/取消任务等应能被合理支持。
- 未知与实验参数有出口：有适当安全校验的自定义端点、Header、请求字段或模板能力，便于尝鲜尚未适配的新厂商。
- 真实失败可解释：401、限额、地域、权限、参数冲突、模型停服、网络超时等要给出可操作的诊断。
- 不规定技术栈：由 Agent 根据规模、可靠性、扩展性、部署与维护成本选型；可考虑本地优先，但不要提前锁死 Web、桌面或云端形态。
- 避免过度工程化：不为尚未发生的问题提前引入复杂基础设施；优先完成真实 API 的端到端体验。
7. 凭证、费用、隐私与安全
这一项目可能连接多个付费账户且处理语音、文件、图片和视频，需要有基本底线：
- 便于管理多个厂商、多个账号/Key、不同 Base URL 或区域端点；密钥不得出现在可分享实验、普通日志、截图或脱敏后的导出内容中。
- 对昂贵视频/多模态任务提供成本或资源消耗提示，支持可理解的预算控制；不在未经确认的情况下进行大额批量调用。
- 允许查看请求内容，但敏感 Headers、凭证等默认隐藏；本地/云端存储策略应清楚可控。
- 声音克隆、真人肖像、电脑操作、外部工具执行等需要遵守授权及相关接口规则，对有实际副作用的动作进行适当确认。
- 不主动绕开厂商权限、速率限制或服务条款；对受限能力明确标注，不伪造调用成功。

9. 开发方式与自主决策空间
期望 Agent 采取研究—实现—真实验证—迭代的闭环，而不是先写一份巨大的静态配置表。建议的工作方式：
1. 盘点能力与机会：结合官方文档、SDK、更新日志及必要的社区反馈，建立可追踪的厂商/模型/特性线索。明确来源、验证日期、权限和不确定性。
2. 做小而完整的纵向切片：先完成从配置连接、填写原生参数、实际调用、观察结果、保存实验到错误处理的一整条链路；尽早包含至少一种真正有特色的 API 和一种非纯文本形态。
3. 抽象已经重复的部分：先以真实差异建立适配机制，再沉淀可复用组件；避免为了抽象牺牲原生能力。
4. 逐步扩展广度和深度：根据趣味性、价值、API 可用性、成本、维护负担选择下一批厂商和玩法，必要时修正产品结构。
5. 持续校验现实：文档所称支持、实际账号可用、实测成功、特性完整、暂不可用等状态要分开记录。
Agent 可以自主选择架构、技术、界面风格、组件库、接口抽象、开发工具及测试方案，也可提出超出本文的新玩法。只有涉及付费额度、外部账号权限、重大需求取舍或不可逆操作时，才需要就相关决策征求我的确认；一般工程细节无需逐项请示。
10. 怎样算做对了：验收关注点
最终更关注体验和可靠性，而不是固定的目录结构、页面数量或代码行数。希望实际演示能证明：
- 易用：添加 API、找到模型/特性并完成首次调用的步骤简洁，不需要为每个实验先手写 HTTP 请求。
- 深度：真正存在可工作的厂商原生能力与专用交互，不只是一个通用聊天框加自定义 JSON。
- 多模态：可以对真实非文本输入/输出或实时/异步任务进行正确的交互与结果查看，不用文本占位伪装。
- 准确：参数有效性、模型支持、权限、地域、费用和接口限制清楚可见，能力标记有验证依据。
- 透明：可以追溯原始请求/响应、流式事件、错误信息、耗时和可获得的用量；必要时定位问题。
- 可复现：实验有记录，可回放参数、复用素材和比较结果；长任务不会因前端刷新而无故丢失。
- 易扩展：添加新厂商和新特色时，不用复制整套 UI 或大规模改动无关模块。
- 可信赖：敏感凭证受到保护，付费任务有可控性，明确区分真实调用与模拟/演示数据。
如遇到因权限、费用或账户缺失而无法真实测试的接口，应保留清晰的限制说明与待验证任务，而不是宣称完成。
11. 不希望项目变成什么
- 仅换皮的 ChatGPT/Cherry Studio/Chatbox，或者把所有厂商压扁成 OpenAI Chat Completions。
- 为了展示“支持几百个模型”而接入大量无法验证、无法使用或只有最浅层功能的条目。
- 强制所有厂商共用一套参数，导致特色失效、字段被丢弃或伪兼容。
- 只做静态功能展示，没有真实 API 调用、可观察结果和调试能力。
- 早期过度设计微服务、复杂基础设施或繁琐的插件规范，反而迟迟不能把一个玩法真正跑通。
- 把本文的启发清单当作不可变产品规格，忽略之后更新的模型和更有趣的方向。
12. 希望最终交付什么
请在开发过程中持续维护可供接手的简明材料，并最终提供：
1. 可运行的项目，以及简洁可靠的启动、配置、使用说明。
2. 已经接入的厂商、模型与特性清单，标注验证情况、原生适配深度、已知限制及相关来源。
3. 可直接玩的实验预设/示例，帮助第一次使用者迅速体验重点功能。
4. 真实测试结果与问题清单，包括需要账号、白名单或付费才能继续验证的功能。
5. 面向后续开发者/Agent 的扩展说明，便于添加新的厂商、端点、模态和定制交互。
不要为了交付文档而停止开发；文档是促进实际产品不断变好的工具。初期就应以可运行、可体验的版本为目标，在此基础上继续迭代。
一句话总结：我要的是一个「能不断发现和玩透国内外各种 AI API 原生特性」的多模态游乐场。它必须让体验足够简单，让深度探索足够自由；底层可以统一，厂商真正独特的能力不能被统一掉。
