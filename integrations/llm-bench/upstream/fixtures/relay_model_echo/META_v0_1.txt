gate:
  correct != 200                      -> REQUEST_FAILED
  correct 200 but content_len == 0    -> EMPTY_BODY
  any probe transient (429/5xx/none)  -> INCONCLUSIVE_TRANSIENT
  typo 2xx                            -> SILENT_FALLBACK
  bad_prefix 2xx                      -> PARTIAL_REJECT
  both non-2xx, model absent          -> REJECTS_AND_NO_FIELD
  both non-2xx, model == request      -> REJECTS_AND_ECHO
  both non-2xx, model != request      -> MISMATCH_REPORTED

  2233 ms; typo 404 / 13 ms; bad prefix 404 / 0 ms.
no real host, key or provider name is present; live probing is opt-in via --probe.
detail subcodes (detail only; the verdict set above is unchanged):
  404 body "no adapter registered for provider" -> PROVIDER_UNKNOWN
  404 body "could not be resolved" (+ listing)  -> MODEL_UNKNOWN
  both shapes carry the same error code
  ("model_not_found"), so a client keying on "code" cannot tell "this model does
  not exist" from "this provider does not exist" - only the message can. That is
  the whole reason this is a detail and not a verdict: the verdict family is
  identical, the actionable next step is not (drop the model vs drop the whole
  provider from the pool).
  classification reads the typo probe body first (it is the one that can say "no
  such model"), then the bad-prefix body (the one that can say "no such provider").
